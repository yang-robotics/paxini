# 时间戳说明

这份文档只讲时间：**每列数字到底是什么时刻、谁打的、能不能比**。
字段本身的形状和单位见 [`HDF5结构说明.md`](HDF5结构说明.md)。

---

## 0. 先说结论

采集里有三个来源，**三把不同的尺子**：

| 来源 | 能给出绝对时刻吗 | 凭什么 |
|---|---|---|
| 手套 | **能** | SDK 在**主机侧**打戳：组好一整帧、调用回调之前读一次主机钟 |
| 相机 | **能** | 主机打戳（ffmpeg 直接写墙钟） |
| Quest（SDK 四列） | **暂时不能** | SDK 给了四列，但**时钟起点官方没写**，不知道基准在哪 |
| Quest（`host_unix_ns`，format 5 起） | **能** | 采集进程在 `collect_sample()` 前后读主机钟；这是**PC 接收时刻**，不是头显采样时刻 |

"绝对时刻"指能换算成 `2026-11-13 10:50:00.123` 这种。手套和相机都能，
而且**两者含义其实一样**：都是"这一帧在主机上可用的时刻"，差别只在链路长短
（手套走串口，相机走 UVC + ffmpeg），见 §2 与 §4.2。

Quest 的四列约定为主机墙钟（**未经 C8 实证**），下游按这个约定参与对齐，产物里标
`clock_domain_verified=false`。没有实证前，跨源比较的地基是「约定」而不是「测量」。

## 1. 一张总表

![三个来源把时间戳打在不同位置](figures/timestamp-paths.svg)

横轴是一条链路消耗掉的时间。手套和相机的戳都打**在主机侧**、帧收齐之后：手套前面是串口传输 + SDK 组帧，相机前面是曝光、编码、USB、缓冲（几十毫秒，随负载抖动）；Quest 的戳**位置不明**——SDK 没公开基准。看这张图记住一件事：戳的差值一半是时钟差、一半是链路延迟，两者要分开处理。**设备端不参与打戳**，所以也不存在"手套自己校时"这回事。


| 来源 | 字段 | 谁打的戳 | 时钟 | 起点 | 会跳吗 | 真实含义 |
|---|---|---|---|---|---|---|
| 手套 | `cap/timestamp_unix_ns` | SDK（主机侧） | CLOCK_REALTIME（主机） | 1970-01-01 | **会**（主机校时） | 帧在主机可用的时刻 |
| 手套 | `cap/timestamp_monotonic_ns` | SDK（主机侧） | CLOCK_MONOTONIC（主机） | 主机开机/VM 启动 | 不会 | 同上，换一把尺子 |
| 相机 | `cameras/<id>/timestamp_unix_ns` | 主机（ffmpeg） | CLOCK_REALTIME | 1970-01-01 | **会** | 帧**到达主机**的时刻 |
| Quest | `quest/sdk_timestamp_ns` 等四列 | Quest SDK | **未知** | 未知 | 未知 | 未知 |

两个关键点：

- **两个戳都打在主机侧，都不代表设备采样时刻。** SDK 手册原文："时间戳由 SDK 在
  完整帧组装完成、即将调用回调时记录，表示主机侧回调帧可用时刻，不表示设备硬件采样时刻。"
  所以手套那列也带着串口传输 + 组帧的延迟，只是（串口）比相机（UVC + ffmpeg）短。
- **相机只有墙钟一列**（`timestamp_unix_ns`）。算帧间隔时墙钟跳变会造出假间隔，
  按 §4.1 的方法剔除。

## 2. 逐个数

### 2.1 手套：SDK 在主机侧给两个时钟面

pxhandsdk 每帧同时给两个读数，**都是主机钟、都在同一个瞬间**（SDK 组好这一帧、
调用回调之前），不是设备采样时刻，也不是手套固件打的：

| | `timestamp_unix_ns` | `timestamp_monotonic_ns` |
|---|---|---|
| 起点 | 1970-01-01 UTC | 主机开机或 VM 启动那一刻 |
| 会跳吗 | 会被 NTP 校时 step，**实测跳 2201 ms** | 只增不减 |
| 能干什么 | 和相机比、和文件时间比 | 算帧间隔、算频率 |
| 不能干什么 | 算帧间隔（跳变会算出负间隔） | 跨重启比较，它没有绝对意义 |

**单调钟不是"更准"，是"更连续"。** 它不知道现在几点，只知道过了多久。

算频率必须用它：`rate = (N-1) / (mono[-1] - mono[0]) * 1e9`。用墙钟算的话，
一次校时能把 118 Hz 算成 109 Hz。

### 2.2 相机：ffmpeg 打墙钟

V4L2 驱动本来会给一个时间戳（默认是内核收帧的单调钟），但
`-use_wallclock_as_timestamps 1` 让 ffmpeg 在收帧时读一次主机墙钟并**覆盖它**，
写进容器的就是墙钟。停止后用 ffprobe 读回来，逐帧写进
`cameras/<id>/timestamp_unix_ns`。

这一列**已经是绝对时刻**，不需要任何换算。

### 2.3 Quest：四列，暂时只有相对意义

| 字段 | SDK 方法 | 缺失时 |
|---|---|---|
| `quest/sdk_timestamp_ns` | `get_time_stamp_ns()` | -1 |
| `quest/body_timestamp_ns` | `get_body_timestamp_ns()` | -1 |
| `quest/motion_timestamp_ns` | `get_motion_timestamp_ns()` | -1 |
| `quest/body_joints_timestamp_ns` | `get_body_joints_timestamp()` | -1（24 个关节各自） |

官方 docstring 只有一句 "Get the timestamp in nanoseconds."，**没写起点、没写
基准、没写和系统时钟的关系**。

所以在 C8 跑通之前：

- ✅ 可以算增量（相邻两行的差）、看丢帧
- ⚠️ 与手套/相机的 unix 相减**是工程的约定做法**（老文件默认回退 `--quest-align unix`；新采集用 `host_unix_ns`），
  不是已证实的物理事实；要变成事实就得跑 C8 并走 `sdk_unix`
- ❌ 不能假设它是 unix 纳秒——虽然下游按它当 unix 用，但那是决定，不是证据

C8 的重复判据按**持续时长**算，不按连续行数：120 Hz 轮询比 SDK 更新快，同一时间戳
重复 20 多行是正常的（`data_20261127_4` 最长 26 行 ≈ 0.22 s）；只有同一个值持续
超过 1 s 才判时钟冻结。探针和 `sdk_unix` 的文件级检查用的是同一条规则，所以 120 Hz
采集可以直接跑 `quest_clock_probe.py --duration 60`，不必为了绕开门控降到 30 Hz。

`sequence` 是唯一可靠的：连续递增，跳号说明丢样本。

**format_version 5 起**，`quest/` 另有 `host_unix_ns` / `host_monotonic_ns` 两列：
采集进程在 `collect_sample()` 前后各读一次主机钟、取中点。它和相机/手套的墙钟/单调钟
是同一侧，所以下游 `--quest-align host`（新采集默认 `auto` 会选它）可以直接配对，
不需要 C8 报告。它**不冒充头显采样时刻**：头显 → PC 的传输延迟仍然存在；C8 只验证
SDK 四列的时钟域，不是证明 host 列等于曝光/采样真值。

**工程口径**：`unix`/`sdk_unix` 模式用 `sdk_timestamp_ns`；`host` 模式用
`host_unix_ns`（新采集默认）。`body_` / `motion_` / `body_joints_` 三列照旧写入、
不参与任何对齐或换算（保留是因为丢掉不可再生）。

同一批决定还包括：Quest **默认参与对齐**（新采集 `--quest-align host`/`auto` 用主机接收时刻；老文件 `unix`），取目标时刻之前
最近的一条整行复制，滞后逐行记 `quest/age_ms`；不走四元数插值。没有 Quest 数据的
采集自动跳过，不报错。

## 3. 拿到文件怎么用

### 3.1 这帧是什么时刻

```python
import h5py

with h5py.File("data.h5") as f:
    # 手套：直接用
    t_hand = f["cap/timestamp_unix_ns"][100]          # 第 100 帧的绝对时刻

    # 相机：也直接用（采集端写的就是绝对时刻）
    t_cam = f["cameras/right_cam0/timestamp_unix_ns"][50]

    # Quest：没有绝对时刻，只有 sequence
```

### 3.2 帧间隔和频率

| 来源 | 用什么算 | 为什么 |
|---|---|---|
| 手套 | `diff(timestamp_monotonic_ns)` | 墙钟会跳，跳一次就出负间隔 |
| 相机 | `diff(timestamp_unix_ns)` | 墙钟不跳的话没问题，跳了要按 §4.1 剔除 |
| Quest | 只能看 `diff(sequence)` | 四列时间戳的域未知 |

### 3.3 两个来源能不能对齐

| 组合 | 现在能不能 | 说明 |
|---|---|---|
| 手套 ↔ 相机 | 能，但怕跳表 | 两边都用墙钟。跳了之后跨跳变点的对齐会偏，按 §4.1 剔除 |
| 手套 ↔ Quest | **新采集可以；老文件按约定** | 新采集用 `host_unix_ns` 主机接收时刻（同一主机轴，无需 C8，`summary.quest.alignment=host`、`clock_domain_verified=false`——它验证的是主机接收轴，不是 SDK 时钟域）；老文件 SDK 戳约定为主机墙钟，标 `false` |
| 相机 ↔ Quest | **新采集可以；老文件不能** | 新采集 host 与相机同一主机轴；老文件 SDK 戳未经 C8 |

采集端**不做任何配对**，只保证原始时间戳齐全。谁配谁、阈值多少、要不要插值，
是下游 `Paxini-Align/` 的事。

## 4. 三个坑

### 4.1 墙钟会在采集中途跳（实测 2201 ms）

本机实测：20 秒采集，第 0.85 秒 `unix - monotonic` 的偏移突然变了 2201 ms，
是 NTP 校时。

**采前必须关**：

```bash
sudo timedatectl set-ntp false
```

关掉后重采，最大单步变化 **0.001 ms**。

跳了怎么办：数据仍然是对的，但跨跳变点的跨源对齐会整体偏。检测方法：

```python
offset = f["cap/timestamp_unix_ns"][:] - f["cap/timestamp_monotonic_ns"][:]
jumps = np.flatnonzero(np.abs(np.diff(offset)) > 5_000_000)   # >5 ms
```

ffmpeg 每帧现读墙钟，跳变**直接写进戳里**，那一段会出现 ±2 秒的假帧间隔，差分要
先把跳变点剔除。所以采集前必须关 NTP。

### 4.2 相机的戳是"到达"不是"曝光"

UVC 协议里没有绝对时间。V4L2 给的是内核收帧的单调钟（随后被 ffmpeg 覆盖成墙钟），
所以存下来的是**主机的接收时刻**，包含：

```text
曝光时间 + MJPEG 编码 + USB 传输 + 驱动缓冲 + ffmpeg 处理
```

这段延迟几十毫秒，且随负载抖动。**不要指望相机时间戳能对上手套的采样时刻**，
能做到的是"同一时刻附近 ±几十毫秒"。手套那侧同理：它的戳也会晚于采样，
晚的是"串口传输 + SDK 组帧"，量级比相机小但同样不是零。

修正这段延迟用 `Cap_Quest/latency/measure_camera_latency.py`，测出来的 Δ 是
「墙钟 pts 本身减曝光时刻」，量级几十毫秒。

每次测量都追加进 `Cap_Quest/latency/records/<电脑用户>-ubuntu.yaml`，一台机器一个
文件、一条一个序号。**下游取数读这个文件里最近一次 `ok: true` 的记录**，不要把某个
数字写死：同一台机器连测，链路整体跳档时三次能差 100 ms 以上，而每次的 IQR 都只有
几毫秒——跳的是链路，不是抖动。

**没有台账时下游按「未标定」处理：Δ=0，并在 stderr 告警、在产物 summary 里写
`camera_delay_source`。** 2026-11-20 之前这里有个 192.3 ms 的兜底默认值，那是旧
Windows 采集路径在某台机器上的读数，V4L2 路径上没有任何依据；套用它会让整条时间轴
偏 100+ ms，而行数、间隔、单调性全都正常，事后基本查不出来。

### 4.3 Quest 的 -1 不是时间

四列都用 `-1` 表示"SDK 没给这个值"。算差分会得到 0 或负数，必须先用 `> 0` 过滤：

```python
mask = stamps > 0
delta = np.diff(stamps[mask])
```

## 5. 验证到哪一步了

| 项 | 状态 |
|---|---|
| 手套两个时钟的实测值 | ✅ 118.29 Hz，帧间隔 p95 8.96 ms |
| 相机（V4L2） | ✅ 原生路径已跑通（A12：640×480@15 联合采集；720p30 双路长时待复测） |
| 相机延迟 Δ | ✅ 两路已测（2026-11-21）：cam0 **84.7 ms**、cam1 **87.6 ms**，台账 `Cap_Quest/latency/records/ifnot-ubuntu.yaml` |
| 墙钟跳变 | ✅ 实测 2201 ms，关 NTP 后 0 |
| Quest 基础采集与四列输出 | ✅ 真机已跑通，2400 行并保留四个 SDK 时间戳字段 |
| Quest 四列时钟域（C8） | ⚠️ 未实测；探针/门控已按“重复持续时长 >1 s”修正，可跑 60 s 探针取 `models.host_unix`；新采集默认 `auto` 用 `host_unix_ns`；老文件才回退 `unix` |

浏览器回放中的 Quest 面板**默认**是 `--quest-align auto`：新采集有
`quest/host_unix_ns`，按主机接收时刻画在手套首帧起的相对 Unix 轴上，标「已按主机
接收时刻对齐（无需 C8）」；老文件没有 host 列才回退 `sdk_timestamp_ns`（标「已按
Unix 墙钟对齐（未经 C8 验证）」）；只有 `sdk_unix` 模式才标「已按 C8 验证的时钟
对齐」。`--quest-align none` 回到独立时间轴并标注「未做跨源时间对齐」，共用播放按钮
只表示归一化进度联动。SDK 时间戳不可用时，Quest 横轴降级为 `sequence`。

要把「约定」变成「实证」，先**单独**运行 `diagnostics/quest_clock_probe.py`
（不在采集里跑，也不进 Align 内部）。探针把主机接收区间写入独立的 `clock_probe/`
报告，不写 `data.h5`；只有报告 `passed=true`，查看器和 Align 才接受
`--quest-align sdk_unix --quest-clock-report <report.json>`。新采集默认 `--quest-align auto` 会走 `host_unix_ns`（免报告）；老文件才回退 `unix`。

```bash
python3.10 diagnostics/quest_clock_probe.py --duration 60 --rate 30 --start-pc-service
python3.10 Paxini-Align/align_capture.py <录制目录>   --quest-align sdk_unix --quest-clock-report clock_probe/run_*/report.json
```

报告里的 `models.host_unix.offset_median_s` 就是这次实测的 SDK↔主机 Unix 偏移；
`data_20261127_4`/`_2` 两份是 **+2.55 / +2.56 s**，所以老文件的默认 `unix` 会把 Quest 整体放晚
约 2.55 s。`sdk_unix` 用仿射模型把它换算掉。报告绑定探针那一刻；头显或 PC 重新校时后
要重跑。manifest 里分开记了按键主机时刻和首个 Quest 样本的 SDK 戳，但**两者跨时钟域，
不能直接相减**（constraints §7）；要量偏移只能跑探针。

细节和判据见 [`待验证清单.md`](待验证清单.md)。
